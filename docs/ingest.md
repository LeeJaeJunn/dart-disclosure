# 공시 파싱 · 청킹 · 임베딩 · 적재

DART 공시 원문(`document.xml`)을 DB의 `filing`, `filing_table`, `chunk` 행으로 바꾸는 과정을 설명한다.
코드는 `backend/src/parsing/`, `backend/src/chunking/`, `backend/src/embedding/`에 있고, 세 단계를 잇는 파이프라인과 DB 적재는 `backend/src/ingest/`에 있다.
DB 테이블 컬럼 설명은 [AGENTS.md](../AGENTS.md)의 DB 구조를 참고한다.

예시는 모두 삼성전자 사업보고서 (2023.12), 접수번호 `20240312000736`을 실제로 처리한 결과다.

## 1. 전체 흐름

```
Disclosure (list.json 한 건)
  │  fetch_document()      DART 응답 ZIP을 풀어 본문 XML({접수번호}.xml) 문자열로
  ▼
본문 XML
  │  parse_document()
  ▼
ParsedDocument             목차 트리 + 본문 블록 + 표
  │  chunk_document()
  ▼
ChunkedDocument            filing 정보 + 표 레코드 + 청크
  │  embed_texts()
  ▼
IngestResult               ChunkedDocument + {text 해시: 1536차원 벡터}
  │  save_filing()         한 트랜잭션으로 공시 1건을 교체 저장 (5장)
  ▼
filing / filing_table / chunk
```

`src/ingest/pipeline.py`의 `ingest_filing()`이 DB 적재 전까지를 한 번에 실행한다. 각 단계 함수의 리턴값을 다음 단계 함수에 넘긴다(`parse_document()` → `chunk_document()` → `embed_texts()`). 중간 결과는 파일로 저장하지 않고, 최종 결과만 DB에 저장한다.

### 파일 (`src/ingest/`)

| 파일 | 역할 |
|---|---|
| `__main__.py` | 실행 명령. `list.json`으로 공시 정보를 찾고 → `ingest_filing()` → `save_filing()` |
| `pipeline.py` | `ingest_filing(disclosure, config)` → `IngestResult`. DART 원문 받기 → 파싱 → 청킹 → 임베딩. DB를 쓰지 않는다 |
| `loader.py` | `save_filing(conn, result)`. `IngestResult`를 DB에 저장한다. 적재 SQL은 이 파일에만 둔다 (5장) |

DART 호출은 모두 `src/dart/client.py`를 쓴다. `fetch_disclosures()`(`list.json`)는 `__main__.py`가, `fetch_document()`(`document.xml`)는 `pipeline.py`가 부른다.

예전의 `python -m src.parsing`, `python -m src.chunking` 명령과 그 중간 결과 파일(`data/parsed/`, `data/chunks/`의 JSON), 임베딩 캐시 파일은 없앴다. 단계별로 따로 실행하지 않고 위 실행 명령 하나로 처리한다.

### 실행 명령 (`backend/`에서)

```bash
uv run python -m src.ingest 20240312000736 --corp-code 00126380
```

- 접수번호와 기업 고유번호를 받는다. 접수번호 앞 8자리(접수일)와 고유번호로 `list.json`을 한 번 조회해 공시명·접수일 등을 찾는다. 못 찾으면 종료한다.
- DB(`DATABASE_URL`)에 테이블이 이미 있어야 한다. 이 명령은 스키마를 만들지 않는다.
- **같은 접수번호가 DB에 있으면 지우고 다시 넣는다.** 이때 그 공시의 `analysis`도 함께 지워진다(5장). 이미 분석 보고서가 있는 공시를 시험 삼아 다시 넣지 않는다.
- Windows에서는 psycopg 비동기 연결 때문에 `SelectorEventLoop`로 실행한다(코드에 들어 있다).
- 끝나면 다음처럼 한 줄을 출력한다. 임베딩 진행 상황(`[embed] 100/1669개` 등)도 중간에 출력한다.

```
[ingest] 삼성전자 사업보고서 (2023.12) (20240312000736): 표 511개, 청크 3150개 (임베딩 1669개)
```

- 시험으로 넣은 공시는 `DELETE FROM filing WHERE rcept_no = '<접수번호>';` 한 줄로 지운다. `filing_table`, `chunk`, `analysis`는 `ON DELETE CASCADE`로 함께 지워진다.

### 코드에서 쓰기

```python
from src.ingest.pipeline import ingest_filing

result = await ingest_filing(disclosure)  # disclosure: fetch_disclosures()가 돌려준 Disclosure
# result.document.filing, result.document.tables, result.document.chunks → DB 행
# result.embedding(chunk) → chunk.embedding 값 (embed=false면 None)
```

- `filing.is_latest`는 여기서 정하지 않는다. 적재할 때 DB에서 같은 기간 공시끼리 비교해 정한다(5장).
- `config=ChunkingConfig(...)`로 청크 길이 설정을 바꿀 수 있다(3.10).
- ZIP에는 본문 외에 감사보고서 등 첨부 파일이 함께 오지만 본문만 쓴다. 본문이 없으면 `ValueError`를 낸다.
- 원문 XML은 DB에 보관하지 않는다. 파서·청커 규칙을 바꿔 다시 처리할 때는 DART에서 원문을 다시 받는다. 공시는 접수 후 바뀌지 않고 정정공시는 새 접수번호로 나오므로, 같은 접수번호로 받으면 같은 원문이 온다.

## 2. 파싱 (`src/parsing/`)

| 파일 | 역할 |
|---|---|
| `document.py` | XML → 목차 트리. 표 앞뒤의 제목·단위·기준일·안내 문구를 표에 연결 |
| `tables.py` | `<TABLE>` → 2차원 격자 → 헤더/본문 분리 → 셀 타입·단위 결정 |
| `models.py` | 결과 스키마 (Pydantic) |

현재 버전은 `PARSER_VERSION = "p6"`(`document.py`)이다. 파싱 결과가 달라지는 수정을 하면 이 값을 올린다.

### 2.1 결과 구조

```
ParsedDocument
├── parser_version  "p6"
└── root: ParsedSection            (level 0, 표지처럼 섹션 밖에 있는 내용)
    ├── title, level, path         path 예: ["III. 재무에 관한 사항", "1. 요약재무정보"]
    ├── blocks: [TextBlock | TableBlock]   문서에 나온 순서 그대로
    │     TextBlock  {kind: "text",  text}
    │     TableBlock {kind: "table", table: ParsedTable}
    └── children: [ParsedSection]  하위 섹션
```

삼성전자 예시의 목차 트리 일부:

```
0 ROOT                                  (표지 블록 7개)
  1 I. 회사의 개요
    2 1. 회사의 개요                    (블록 32개)
    2 2. 회사의 연혁
  1 III. 재무에 관한 사항
    2 1. 요약재무정보                   (블록 4개)
    2 3. 연결재무제표 주석              (블록 241개)
  1 IV. 이사의 경영진단 및 분석의견     (하위 섹션 없이 블록 81개)
  ...
```

### 2.2 목차 트리 만들기

1. 전처리: DART 전용 엔티티(`&cr;`, `&crlf;`, `&nbsp;`)를 공백으로 바꾸고 XML 선언을 지운 뒤 `BeautifulSoup(xml, "lxml")`로 읽는다.
2. `<SECTION-1>`, `<SECTION-2>` 태그가 섹션이 된다. 태그 번호가 `level`이고, 섹션 안 `<TITLE>`이 제목이다. 제목이 없으면 `(제목 없음)`이 들어간다.
3. `<BODY>`, `<PART>`, `<LIBRARY>` 같은 껍데기 태그는 건너뛰고 안쪽만 본다.
4. 섹션 밖에 있는 내용(표지 등)은 root(level 0)에 넣는다. `<DOCUMENT-NAME>`, `<COMPANY-NAME>`, `<SUMMARY>` 같은 문서 정보 태그는 본문이 아니므로 뺀다.
5. 섹션 안의 내용은 문서 순서대로 세 가지 항목으로 모은다.
   - 문단(`<P>` 등) → 텍스트
   - 데이터 표 → 표
   - 레이아웃 표 → 표 앞뒤 문맥 후보(2.3)
   - `<TABLE-GROUP>`은 묶음 제목과 `ACLASS`의 XBRL 코드(예: `{XBRL}NT_S_D822405`)를 기억해 두었다가, 안에 있는 표에 `group_title`, `xbrl_code`로 넣는다.

### 2.3 데이터 표와 레이아웃 표

DART 원문은 제목·단위·기준일도 `<TABLE>`로 배치하는 경우가 많다. 그래서 표를 두 종류로 나눈다.

| 구분 | 판단 기준 | 처리 |
|---|---|---|
| 데이터 표 | `BORDER` 속성이 있고 0이 아님. `BORDER`가 없으면 2행 이상이면서 2열 이상 | `ParsedTable`이 된다 |
| 레이아웃 표 | `BORDER="0"`, 또는 `BORDER`가 없고 1행이나 1열 | 셀을 줄글로 펴서 문맥 후보로 둔다. 예: `가. 요약연결재무정보`, `(단위 : 백만원)` |

### 2.4 표를 격자로 펴기 (`tables.py`)

- 셀 태그는 `TD`, `TH`, 그리고 DART 전용 `TE`, `TU`이다.
- `colspan`과 `rowspan`으로 병합된 셀은 차지하는 모든 칸에 같은 값을 복사한다. 그래서 모든 행이 같은 열 수를 가진다.
- 표 안의 표는 바깥 표의 셀로 보지 않는다.
- 값이 전부 빈 행은 버린다.

**헤더 정하기**

1. `<THEAD>` 안의 행, 또는 셀이 전부 `TH`인 행이 앞에서부터 이어지면 그 행들이 헤더다. 그런 행이 없으면 첫 행을 헤더로 본다.
2. 헤더가 여러 행이면 열마다 위에서 아래로 ` / `로 잇는다. 병합 때문에 같은 값이 연달아 나오면 한 번만 쓴다.
3. 본문 첫 행이 첫 칸은 비어 있고 나머지가 모두 날짜나 기간(`2023년 12월말`, `제55기`, `당기`, `3개월`, `누적` 등)이면, 그 행을 헤더로 올린다.

결과 예:

```
header = ["구 분", "제55기 / 2023년 12월말", "제54기 / 2022년 12월말", "제53기 / 2021년 12월말"]
```

### 2.5 표 앞뒤 문맥을 표에 붙이기 (`document.py`의 `_link_tables`)

**표 앞 문맥(`context_before`)**

표 바로 앞 항목부터 거꾸로 올라가며 최대 4개까지 모은다. 다음 경우에는 멈춘다.

- 텍스트가 120자를 넘거나 레이아웃이 200자를 넘는 경우. 단, `단위:`가 들어 있으면 길어도 계속 모은다.
- 소제목을 이미 만났는데 그 위 항목이 소제목이 아닌 경우. 소제목 위의 글은 앞 내용에 속한다고 본다.
  - 소제목은 `I.`, `1.`, `가.`, `(1)`, `1)`, `①`, `(가)`, `가)`, `[..]`, `<..>`, `【..】`로 시작하는 줄이다.
  - `(단위 : 원)`이나 `[△는 부(-)의 값임]`은 소제목으로 보지 않는다.

모은 문맥에서 표에 가까운 쪽부터 다음 값을 찾는다.

| 필드 | 찾는 방법 | 예 |
|---|---|---|
| `unit_raw` | `단위 :` 뒤의 글자 | `백만원`, `백만원, %` |
| `as_of` | `기준일 :` 뒤의 글자 | `2023년 12월 31일` |
| `period_label` | 레이아웃 셀 중 `당기`, `전기`, `전전기`, `당분기말` 등과 정확히 같은 것 | `당기` |
| `title` | 문장이 아닌 짧은 줄(텍스트 40자, 레이아웃 80자 이하)의 첫 줄. 날짜, 기간, `제55기`, 안내 문구, `기준일` 줄은 뺀다. 못 찾으면 `group_title`을 쓴다 | `가. 요약연결재무정보` |

**안내 문구(`notes`)**

- 다음 줄을 안내 문구로 본다.
  - `※`, `*`, `△`, `▲`, `주1)`, `(주)`, `[주`로 시작하는 줄
  - `부(-)`가 들어 있는 줄
  - 단, `단위:`가 들어 있으면 안내 문구가 아니다.
- 표 **바로 뒤**에 이어지는 안내 문구는 그 표의 `notes`에 넣는다.
- 표 앞 문맥 안에 있는 안내 문구 레이아웃도 `notes`에 넣는다.

**본문에서 빠지는 것**

- 제목·단위·기준일·기간 정보를 꺼내 쓴 레이아웃 표와, `notes`로 옮긴 레이아웃 표는 `TextBlock`으로 남기지 않는다. 같은 글이 두 번 나오지 않게 하기 위해서다.
- `(단위 : 원)`만 있는 텍스트 줄도 뺀다.
- 일반 문단은 `context_before`에 들어가도 `TextBlock`으로 그대로 남는다.

### 2.6 연결/별도 구분 (`basis`, `basis_source`)

**왜 필요한가.** 사업보고서에는 같은 "매출액" 표가 두 번 나온다. 연결(종속회사까지 합친 숫자)과 별도(회사 하나만의 숫자)다. 값이 다르기 때문에 표마다 어느 쪽인지 붙여 두어야 "삼성전자 연결 매출액"을 물었을 때 별도 표 숫자로 답하지 않는다.

**어떻게 판단하나.** 표에는 "이 표는 연결입니다"라는 칸이 따로 없다. 그래서 표 주변의 단서 세 가지를 믿을 만한 순서대로 본다. 앞 단서에서 답이 나오면 뒤는 보지 않고, 무엇으로 정했는지를 `basis_source`에 남긴다.

| 순서 | 보는 곳 | 판단 규칙 | 예 | `basis_source` |
|---|---|---|---|---|
| 1 | 표를 감싼 `TABLE-GROUP`의 XBRL 코드 | 코드 중간이 `_C`면 연결, `_S`면 별도 | `{XBRL}NT_S_D822405` → 별도 | `xbrl` |
| 2 | 표가 들어 있는 섹션 경로 | 경로에 `연결재무제표`가 있으면 연결. 섹션 제목이 정확히 `N. 재무제표` 또는 `N. 재무제표 주석`이면 별도 | `III. 재무에 관한 사항 > 3. 연결재무제표 주석` → 연결 | `section_title` |
| 3 | 표 제목 + 표 **앞** 문맥(`context_before`) | 연결 쪽 표현만 있으면 연결, 별도 쪽 표현만 있으면 별도 | `가. 요약연결재무정보` → 연결 | `preceding_heading` |
| 4 | — | 위에서 못 정했거나, 3에서 연결·별도 표현이 둘 다 나옴 | 임원 현황 표 | `unknown` (`basis_source = null`) |

**3번이 표 앞뒤 맥락과 연결되는 부분이다.** 2.5에서 표 앞 최대 4줄을 `context_before`로 모았는데, 그 줄들과 표 제목을 이어 붙여 단어를 찾는다.

- 연결로 보는 표현: `요약연결`, `연결` + `기준`·`재무`·`손익`·`포괄`·`자본변동`·`현금흐름` (예: `연결 기준`, `연결재무상태표`)
- 별도로 보는 표현: `요약별도`, `별도` + 같은 단어들 (예: `별도 기준`, `별도손익계산서`)
- `연결`만 있는 경우는 세지 않는다. `연결대상 종속회사 현황` 같은 표가 연결 재무 표로 잘못 붙지 않게 하기 위해서다.
- 120자를 넘는 긴 문장은 빼고 본다. 본문 설명 속에 지나가듯 나온 "연결"을 표의 제목으로 착각하지 않게 하기 위해서다.
- 표 **뒤** 안내 문구(`notes`)는 보지 않는다. 안내 문구는 "△는 음수" 같은 값 읽는 법이지, 표의 기준을 정하는 제목이 아니기 때문이다.

예를 들어 삼성전자 요약재무정보 표는 XBRL 코드가 없고, 섹션 경로(`III. 재무에 관한 사항 > 1. 요약재무정보`)에도 단서가 없다. 그래서 3번으로 넘어가 앞 문맥 `["가. 요약연결재무정보", "(단위 : 백만원)"]`에서 `요약연결`을 찾아 `basis = consolidated`, `basis_source = preceding_heading`이 된다(2.8의 JSON 예시).

삼성전자 결과(표 511개): xbrl 연결 169 · 별도 142, preceding_heading 연결 3 · 별도 1, unknown 196.
unknown은 대부분 재무 외 섹션의 표다(임원, 주주, 계열회사 등). 원래 연결/별도 구분이 없는 표라서 unknown이 맞다.

### 2.7 셀 (`Cell`)

```json
{"row": "[유동자산]", "column": "제55기 / 2023년 12월말", "raw": "195,936,557", "type": "number", "unit": "백만원"}
```

| 필드 | 내용 |
|---|---|
| `row` | 행 라벨, 즉 그 행의 첫 칸 값. 첫 칸 자신은 `""` |
| `column` | 그 열의 헤더 (2.4) |
| `raw` | 원문 값 그대로. 쉼표, `△`, 괄호, `%`를 지우거나 바꾸지 않는다 |
| `type` | 아래 순서로 판단 |
| `unit` | `type`이 `number`일 때만 채울 수 있다 (아래) |

**`type` 판단 순서**

1. `empty`: 빈칸, 또는 `-`, `−`, `–`, `—`, `ㅡ`만 있는 칸
2. `date`: `2023년`, `2023년 12월말`, `2023년 12월 31일`, `2023.12.31`, `2023-12` 등
3. `number`: `1,234`, `△1,234`, `-1,234`, `(1,234)`, `1.5`
4. `percent`: `12.3%`, `△1.2%`, `(1.2)%`
5. `text`: 나머지 전부

삼성전자 예시 셀 수: text 23,315 · number 12,434 · empty 11,077 · date 2,095 · percent 299

**`unit` 규칙**

먼저 표 단위가 하나일 때만 셀 단위를 정한다. `unit_raw`에 `,`, `/`, `·`가 있으면(예: `백만원, %`) 어느 열이 어떤 단위인지 모르므로 모든 셀의 `unit`을 비운다.
표 단위가 하나이면 숫자 셀마다 행 라벨과 열 이름을 보고 아래 순서로 판단한다.

| 순서 | 경우 | 결과 | 예 (표 단위 `백만원`) |
|---|---|---|---|
| 1 | 라벨·열 이름에 표와 **다른** 단위가 괄호로 적힘 | 비움 | `주당이익(원)` |
| 2 | 라벨·열 이름에 표와 같은 단위가 적힘, 또는 표 단위가 금액이 아님(`주`, `%`, `명` 등) | 표 단위 | `매출액(백만원)` |
| 3 | 금액이 아닌 항목(`직원수`, `인원`, `주식수`, `발행주식`, `수량`, `건수`, `근속`, `연령` 등) | 비움 | `직원수` |
| 4 | 주당 금액이고 표 단위가 `원`이 아님 | 비움 | `기본주당이익` |
| 5 | 비율 항목(라벨 조각이 `율`/`률`로 끝남. `환율`, `법률`은 제외) | 비움 | `부채비율` |
| 6 | 그 밖 | 표 단위 | `매출채권` → `백만원` |

**원칙:** 파서는 값의 의미를 확정하지 않는다. `△`나 괄호가 음수인지, `손실` 행의 부호가 어떤지는 `notes`(예: `[△는 부(-)의 값임]`)를 보고 LLM이 판단한다. 공시마다 표기 규칙이 달라서, 파서가 잘못 바꾸면 원문 근거와 값이 어긋나기 때문이다. 단위도 확실할 때만 채우고, 애매하면 비운다.

## 3. 청킹 (`src/chunking/`)

| 파일 | 역할 |
|---|---|
| `chunker.py` | `chunk_document(document, filing, config)` → `ChunkedDocument` |
| `models.py` | `FilingInfo`, `ChunkingConfig`, `Chunk`, `TableRecord`, `ChunkedDocument` |

### 3.1 입력: `FilingInfo`

파이프라인이 DART `list.json` 결과(`Disclosure`)에서 받는 값과, 그 값에서 계산하는 값이 있다.

| 필드 | 출처 | 예 |
|---|---|---|
| `rcept_no`, `corp_code`, `corp_name`, `report_nm`, `rcept_dt` | `Disclosure` | `20240312000736`, `00126380`, `삼성전자`, `사업보고서 (2023.12)`, `20240312` |
| `is_latest` | 기본값 `true`. 적재할 때 DB에서 다시 계산한다(5장) | `true` |
| `report_type` | `report_nm`에 `사업보고서`, `반기보고서`, `분기보고서` 중 하나가 있으면 그 이름. 없으면 `report_nm` 그대로 | `사업보고서` |
| `period` | `report_nm`의 `(YYYY.MM)`. 없으면 `rcept_dt`의 연·월 | `2023.12` |
| `dart_url` | `https://dart.fss.or.kr/dsaf001/main.do?rcpNo=<rcept_no>` | |

### 3.2 출력: `ChunkedDocument`와 DB의 대응

| `ChunkedDocument` | DB | 비고 |
|---|---|---|
| `filing` + `parser_version` + `chunker_version` | `filing` 1행 | |
| `tables[]` (`TableRecord`) | `filing_table` 행 | `ParsedTable` + `table_id`, `rcept_no`, `section_id`, `table_index`. `rows`는 DB의 `cells` 컬럼 |
| `chunks[]` (`Chunk`) | `chunk` 행 | `embed` 필드는 DB 컬럼이 아니다. `embed=true`인 청크만 `embedding`을 채우고, 나머지는 `NULL` |
| `config` | 없음 | `chunker_version`에 해시로 남는다 (3.9) |

### 3.3 섹션 순회와 ID

- 목차 트리를 위에서부터 깊이 우선(전위)으로 돈다. 내용이 없는 root는 건너뛴다.
- 모든 섹션은 내부 노드라도 각자 청크를 만든다. 하위 섹션의 내용은 상위 섹션 청크에 들어가지 않는다.
- ID는 모두 md5 앞 16자리다. 같은 공시를 같은 규칙으로 다시 처리하면 같은 ID가 나온다.

| ID | 만드는 값 |
|---|---|
| `section_id` | `rcept_no` + 경로 제목들. 같은 경로가 또 나오면 순번을 붙인다. root는 경로 `["표지"]` |
| `table_id` | `section_id` + `"table"` + 섹션 안 표 순번 |
| `chunk_id` (section) | `section_id` + `"section"` |
| `chunk_id` (text) | `section_id` + `"text"` + 섹션 안 text 청크 순번 |
| `chunk_id` (table) | `table_id` + 열 묶음 번호 + 행 묶음 번호 |
| `chunk_id` (table_kv) | 짝이 되는 table 청크의 `chunk_id` + `"kv"` |

### 3.4 청크 종류

한 섹션에서 다음 청크가 나온다.

```
섹션 1개 ──► section 청크 1개   (섹션 전체 페이지)
        ├─► text 청크 N개       (본문 문단을 길이로 나눔)
        └─► 표마다
              table 청크 M개    (표를 행·열 묶음으로 나눔)
              table_kv 청크 ≤M개 (같은 묶음을 "라벨(열)=값"으로 편 것)
```

| kind | 내용 | `embed` | `table_id` |
|---|---|---|---|
| `section` | 섹션 전체: 본문 + 모든 표(문맥 줄, 안내 문구, 마크다운 표) | 항상 `false` | 없음 |
| `text` | 본문 문단 묶음 | 항상 `true` | 없음 |
| `table` | 표 일부의 원본 마크다운 | 짝이 되는 KV가 없고, 첫 열을 뺀 값이 있을 때만 `true` | 있음 |
| `table_kv` | 같은 부분을 `행(열)=값 단위` 문장으로 편 것 | 항상 `true` | 있음 |

삼성전자 예시: 표 511개, 청크 3,150개

| kind | embed | 개수 |
|---|---|---|
| section | false | 54 |
| text | true | 157 |
| table | false | 1,427 |
| table | true | 278 |
| table_kv | true | 1,234 |

임베딩 대상은 1,669개이다.

### 3.5 `text`와 `raw`

모든 청크는 `text`와 `raw` 두 가지 본문을 가진다.

| 필드 | 쓰임 | 내용 |
|---|---|---|
| `text` | 임베딩 입력, 키워드 검색 | 머리말 `[회사명 \| 보고서종류 기간 \| 섹션 경로]` + 본문. `text`·`table`·`table_kv`는 6,000자(`max_embed_chars`)에서 자르고, `section`은 자르지 않는다 |
| `raw` | LLM에게 보여 주는 근거 원문 | 머리말 없음. 자르지 않는다 |

머리말을 붙이는 이유: 표 일부나 문단만 보면 어느 회사·어느 보고서·어느 섹션인지 알 수 없다. 머리말이 있어야 "삼성전자 2023 재고자산" 같은 질문과 벡터가 가까워진다.
삼성전자 예시에서 `section` 청크는 54개 중 24개가 6,000자를 넘지만(가장 긴 것 175,278자) 자르지 않는다. 임베딩 대상 청크(`text`, `table`, `table_kv`)는 6,000자에 닿은 것이 없다. `raw`는 어느 경우든 그대로 남는다.

### 3.6 `section` 청크

위키처럼 섹션 하나를 통째로 읽을 때 쓴다. 임베딩하지 않는다.

```
# III. 재무에 관한 사항 > 1. 요약재무정보

가. 요약연결재무정보

### 표 1
가. 요약연결재무정보 | 단위: 백만원 | 연결
※ 한국채택국제회계기준(K-IFRS)에 따라 작성되었습니다.
[△는 부(-)의 값임]
※ 기본주당이익(보통주) 산출근거는 ...
| 구 분 | 제55기 / 2023년 12월말 | 제54기 / 2022년 12월말 | 제53기 / 2021년 12월말 |
|---|---|---|---|
| [유동자산] | 195,936,557 | 218,470,581 | 218,163,185 |
...
```

- 본문과 표를 원문 순서대로 둔다.
- 표마다 `### 표 N`, 문맥 줄(3.8), 안내 문구, 표 전체 마크다운을 넣는다.
- 안내 문구를 표 **위**에 두는 이유: 긴 표를 발췌해 앞부분만 쓰더라도 `△는 부(-)의 값임` 같은 해석 규칙이 함께 남게 하기 위해서다.
- 목차 줄(`4. 매출 및 수주상황 ------ 34`)도 여기에는 남는다.

### 3.7 `text` 청크

섹션의 텍스트 블록만 이어 붙여서 길이로 나눈다.

1. 줄바꿈으로 문단을 나눈다. 목차 줄(`제목 -----… 쪽번호`)은 뺀다.
2. 800자(`max_paragraph_chars`)를 넘는 문단은 `다. `로 끝나는 문장 단위로 나누고, 그래도 길면 800자씩 자른다.
3. 문단을 차례로 쌓는다.
   - 다음 문단을 더했을 때 900자(`target_chars`)를 넘으면 지금까지 쌓은 것을 청크로 만든다.
   - 쌓은 길이가 1,400자(`max_chars`)를 넘어도 청크로 만든다.
4. 다음 청크는 앞 청크의 마지막 1문단(`overlap_paragraphs`)부터 시작한다. 문장이 경계에서 끊겨 문맥을 잃는 것을 막기 위해서다.
5. 겹친 문단만 남고 새 문단이 없는 조각은 버린다.

`meta.chunk_index`에 섹션 안 순번이 들어간다.

### 3.8 `table` 청크와 `table_kv` 청크

**표 나누기**

- **열 방향:** 10열(`max_columns`)을 넘는 넓은 표는 첫 열(행 라벨)을 고정하고 나머지를 9열씩 나눈다. 묶음 번호가 `meta.col_group`이다. 예: 연결 종속기업 목록처럼 회사가 열로 나열된 표
- **행 방향:** 각 열 묶음을 12행(`table_rows_per_chunk`) 또는 약 1,400자(`table_chars`) 중 먼저 닿는 쪽에서 나눈다. 시작 행 번호가 `meta.row_start`(0부터)이다.
- 나눈 조각마다 `table` 청크 1개를 만들고, 조건이 맞으면 `table_kv` 청크 1개를 더 만든다.

**문맥 줄**

두 청크 모두 맨 앞에 표의 문맥 줄을 붙인다. `notes`는 붙이지 않는다. 안내 문구는 `filing_table.notes`에 표마다 한 번만 저장하고, 청크는 `table_id`로 찾아간다.

```
<title> | 단위: <unit_raw> | 연결/별도 | <period_label> | 기준일: <as_of>
```

값이 없는 항목은 빠진다. 예: `가. 요약연결재무정보 | 단위: 백만원 | 연결`

**`table` 청크 예시** (`embed=false`: 짝 KV가 있으므로)

```
[삼성전자 | 사업보고서 2023.12 | III. 재무에 관한 사항 > 1. 요약재무정보]
(표 1, 행 1-10)
가. 요약연결재무정보 | 단위: 백만원 | 연결
| 구 분 | 제55기 / 2023년 12월말 | 제54기 / 2022년 12월말 | 제53기 / 2021년 12월말 |
|---|---|---|---|
| [유동자산] | 195,936,557 | 218,470,581 | 218,163,185 |
| ㆍ현금및현금성자산 | 69,080,893 | 49,680,710 | 39,031,415 |
...
```

- 첫 줄과 `(표 N, 행 a-b)` 줄은 `text`에만 있다. `raw`는 문맥 줄 + 마크다운이다.
- 마크다운 셀 안의 줄바꿈은 공백으로, `|`는 `\|`로 바꾼다. 헤더가 없는 열은 `colN`으로 쓴다.

**`table_kv` 청크 예시** (`embed=true`)

```
[삼성전자 | 사업보고서 2023.12 | III. 재무에 관한 사항 > 1. 요약재무정보]
가. 요약연결재무정보 | 단위: 백만원 | 연결
[유동자산](제55기 / 2023년 12월말)=195,936,557 백만원; [유동자산](제54기 / 2022년 12월말)=218,470,581 백만원; ...
ㆍ현금및현금성자산(제55기 / 2023년 12월말)=69,080,893 백만원; ...
```

- 만드는 조건: 그 조각에서 첫 열을 뺀 셀 중에 `number`, `percent`, `date`가 하나라도 있어야 한다.
- 한 행이 한 줄이다. 셀마다 `행라벨(열이름)=원문값[ 단위]`를 쓰고 `; `로 잇는다. `empty` 셀은 뺀다.
- 단위는 셀의 `unit`이 정해진 경우(2.7)에만 붙인다.
- 마크다운 표는 행 라벨과 열 이름이 멀리 떨어져 있어서, 숫자가 무엇인지 임베딩에 잘 드러나지 않는다. KV 문장은 값마다 항목명과 기간이 바로 옆에 붙어서 검색이 잘 된다.
- 짝 table 청크와 `table_id`, `meta`(`table_index`, `row_start`, `col_group`)가 같다. 그래서 KV로 검색한 뒤 같은 부분의 원본 표를 찾을 수 있다.

**`table` 청크를 임베딩하는 경우**

- KV가 있는 조각: 원본 표는 임베딩하지 않는다. 검색은 KV가 맡고, 원본은 근거 표시에만 쓴다.
- KV가 없는 조각(텍스트만 있는 표): 원본 표를 임베딩한다. 예: 임원 겸직 현황

  ```
  다. 등기임원의 타회사 임원겸직 현황 | 기준일: 2023년 12월 31일
  | 겸 직 자 / 성 명 | 겸 직 자 / 직 위 | 겸 직 회 사 / 기업명 | ... |
  | 김종훈 | 사외이사 | Kiswe Mobile | 회장 | 2013년~현재 |
  ```

- 첫 열을 뺀 셀이 모두 `empty`인 조각: 아무것도 임베딩하지 않는다.

### 3.9 `meta`

모든 청크에 들어가는 필터용 값이다. DB에서 `meta @> '{"corp_code": "00126380"}'`처럼 거를 수 있다(GIN 인덱스).

| 키 | 예 | 설명 |
|---|---|---|
| `corp_code`, `corp_name` | `00126380`, `삼성전자` | |
| `report_nm`, `report_type` | `사업보고서 (2023.12)`, `사업보고서` | |
| `period`, `year` | `2023.12`, `2023` | |
| `rcept_dt` | `20240312` | |

### 3.10 설정과 버전

`ChunkingConfig` 기본값:

| 키 | 값 | 쓰는 곳 |
|---|---|---|
| `target_chars` | 900 | text 청크 목표 길이 |
| `max_chars` | 1400 | text 청크 최대 길이 |
| `overlap_paragraphs` | 1 | text 청크 겹침 문단 수 |
| `max_paragraph_chars` | 800 | 이보다 긴 문단은 나눔 |
| `table_rows_per_chunk` | 12 | 표 조각 최대 행 수 |
| `table_chars` | 1400 | 표 조각 최대 길이(대략) |
| `max_columns` | 10 | 이보다 넓은 표는 열 방향으로 나눔 |
| `max_embed_chars` | 6000 | `text` 최대 길이 (`section` 청크 제외) |

`chunker_version`은 `c3-` + 설정값 md5 앞 6자리이다(예: `c3-cb144e`). 설정을 바꾸면 버전이 자동으로 바뀐다. 청크 규칙(코드)을 바꾸면 `chunker.py`의 `c3`을 올린다.
`filing`과 `analysis`에 `parser_version`, `chunker_version`이 남으므로, 어느 규칙으로 만든 데이터인지 알 수 있다.

## 4. 임베딩 (`src/embedding/`)

```python
from src.embedding.openai import content_hash, embed_texts

texts = [chunk.text for chunk in doc.chunks if chunk.embed]
vectors = await embed_texts(texts)
embedding = vectors[content_hash(chunk.text)] if chunk.embed else None
```

- **대상:** `embed=true`인 청크의 `text`(3.4)
- **모델:** `src/llm/models.py`의 `get_embeddings()`. 모델 이름은 `settings.embedding_model`(기본 `text-embedding-3-small`)이다. 질문을 임베딩하는 `qa/retriever.py`도 같은 함수를 쓰므로, 저장된 벡터와 질문 벡터의 모델이 항상 같다.
- **차원:** 1536. DB `chunk.embedding vector(1536)`과 맞지 않으면 `ValueError`를 낸다. 모델을 바꾸면 DB 컬럼과 기존 벡터도 함께 바꿔야 한다.
- **배치:** 100개씩 `aembed_documents()`로 보낸다.
- **중복 제거:** 반환값의 키는 `text`의 md5(`content_hash`)이다. 같은 내용의 청크는 한 번만 임베딩한다.
- **캐시 없음:** 결과를 파일로 저장하지 않는다. 다시 처리하면 전부 다시 호출하고, 중간에 실패하면 처음부터 다시 한다. 임베딩 모델이 저렴해 공시 1건을 다시 임베딩하는 비용이 작기 때문이다.
- **하지 않는 것:** DB 저장. 파이프라인은 `IngestResult.embedding(chunk)`로 값을 넘기고, 적재 코드가 `chunk.embedding`에 넣는다.

## 5. DB 적재 (`src/ingest/loader.py`)

```python
from src.db.session import pool
from src.ingest.loader import save_filing

async with pool.connection() as conn:
    await save_filing(conn, result)  # result: ingest_filing()의 반환값
```

- **공시 1건 교체:** 한 트랜잭션 안에서 같은 `rcept_no`의 `filing`을 지우고 `filing`, `filing_table`, `chunk`를 다시 넣는다. 몇 번 실행해도 결과가 같고, 중간에 실패하면 아무것도 바뀌지 않는다.
- **`analysis`도 지워진다:** `filing`을 지우면 `ON DELETE CASCADE`로 그 공시의 `analysis`가 함께 지워진다. 규칙이 바뀌어 다시 적재한 공시는 분석도 다시 만든다.
- **값 변환:** 표의 `rows`는 `cells` 컬럼에 jsonb로 넣는다. `chunk.embedding`은 `IngestResult.embedding(chunk)`로 넣고, `embed=false`인 청크는 `NULL`이다.
- **`is_latest`:** 정기보고서(사업·반기·분기보고서)는 저장 후 같은 기업·보고서 종류·기간의 공시 중 접수번호가 가장 큰 것만 `true`로 바꾼다. 접수번호는 접수일 + 순번이라 가장 큰 것이 가장 나중에 접수된 공시다. 정정공시를 넣으면 원래 공시가 `false`가 되고, 옛 공시를 나중에 넣어도 결과는 같다. 정기보고서가 아닌 공시는 `true`로 둔다.
- **스키마:** 테이블을 만들거나 바꾸지 않는다. 컬럼은 [AGENTS.md](../AGENTS.md)의 DB 구조를 따른다.
- 삼성전자 예시를 넣으면 `filing` 1행, `filing_table` 511행, `chunk` 3,150행(임베딩 1,669행)이 된다.

## 6. 설계 원칙 요약

1. **값은 원문 그대로 둔다.** 부호(`△`, 괄호), 손실/수익, 단위가 애매한 값의 해석은 LLM이 `notes`와 문맥을 보고 한다.
2. **확실할 때만 채운다.** 단위, 연결/별도, 제목은 규칙에 맞을 때만 넣고, 아니면 `null`이나 `unknown`으로 둔다.
3. **안내 문구는 표마다 한 번만 저장한다.** `filing_table.notes`에 두고, 청크는 `table_id`로 참조한다.
4. **검색용과 근거용을 나눈다.** 검색은 `text`(머리말 포함, KV 문장), 답변 근거는 `raw`(원본 표, 원문 문단)를 쓴다.
5. **다시 만들 수 있게 한다.** ID는 내용 기반 해시이고, 버전과 설정 해시가 데이터에 남는다.

## 7. 알려진 한계

- `basis = unknown`인 표가 많다(삼성전자 511개 중 196개). 162개는 재무 외 섹션이지만, `financial` 태그 섹션에도 34개가 있다. 이런 표는 LLM이 앞 문맥이나 섹션 경로로 판단해야 한다.
- 표 제목을 못 찾으면 `title = null`이다(삼성전자 511개 중 76개). 이때 청크의 문맥 줄에는 단위·연결 여부만 남는다.
- `section` 청크의 `text`는 자르지 않는다. 삼성전자 예시에서 24개가 6,000자를 넘고 가장 긴 것은 175,278자라, 통째로 LLM에 넘기면 컨텍스트를 크게 차지한다. 나머지 청크는 6,000자에서 잘리지만 지금은 닿는 것이 없다. `raw`는 잘리지 않는다.
- KV 문장의 행 라벨은 원문 그대로(`ㆍ현금및현금성자산`, `[유동자산]`)이다. 상위 항목 이름을 붙이지는 않는다.
- 파서 규칙은 삼성전자 등 사업보고서로 맞춰 왔다. 다른 공시 양식에서는 제목·단위 연결이 다르게 나올 수 있다.
