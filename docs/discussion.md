### 1. `analysis` 테이블 전체 구조 재설계

- 상태: 논의 전 · 등록: 2026-11-11 · 우선순위: 높음
- 방향: 항목별로 고치지 않고 테이블 구조 전체를 다시 설계한다.
- 현재 구조의 문제 (재설계 시 참고)
  - 근거 연결: `sections[].sources[].chunk_id`가 `wiki:...` 형식이라 근거 23개 중 `chunk.chunk_id`와 일치하는 것이 0개다. DB에 없는 별도 저장소(wiki 페이지)를 근거로 만든 것으로 보인다. "모든 요약에 원문 위치를 연결한다"는 규칙을 DB만으로 지킬 수 없다.
  - 검증: `verified: true`의 기준을 DB에서 확인할 수 없다. `check`는 `sources[].verified`로 다시 계산할 수 있는 값이다.
  - 중복·불필요 데이터: `sources[]`의 `url`, `source`, `rcept_dt`, `report_nm`이 `filing`과 중복이다(`rcept_dt`, `report_nm`은 null). `diag`는 디버깅용 진단 정보다.
  - 범위: 8개 고정 섹션(사업 구조, 실적, 주주와 배당 등)은 사업보고서 전용이라 주요사항보고서 등에는 맞지 않는다.
- 확인할 것: 팀원 파이프라인에서 `wiki:` 저장소와 `diag`를 어떻게 쓰는지

### 3. `chunk` 테이블 직접 관리 vs LangChain `PGVector` 사용

- 상태: 논의 전 · 등록: 2026-11-11
- 배경: LLM·임베딩 호출에 LangChain을 도입했다(`src/llm/models.py`). 벡터 저장·검색까지 LangChain에 맡길지 정해야 한다.
- 선택지
  - A. 직접 관리 (현재): 팀원이 설계한 `chunk` 테이블에 직접 저장하고, 검색은 SQL(`ORDER BY embedding <=> 질문벡터`)로 한다. LangChain은 모델 호출에만 쓴다.
    - 장점: 테이블 구조를 자유롭게 설계할 수 있다(`kind`, `table_id`, `section_path` 등). `filing`·`filing_table`과 조인과 필터가 자유롭다. 데이터가 한 벌이다.
    - 단점: 저장·검색 코드를 직접 작성해야 한다.
  - B. LangChain `PGVector` (`langchain_postgres`): `similarity_search()` 등으로 저장·검색을 맡긴다.
    - 장점: 코드가 짧다. LangChain retriever, LangGraph와 바로 연결된다.
    - 단점: LangChain이 정한 테이블(`langchain_pg_collection`, `langchain_pg_embedding`: 본문, `cmetadata` JSON, 벡터)만 쓸 수 있다. 현재 `chunk` 구조를 그대로 쓸 수 없어 데이터를 옮기거나 두 벌로 관리해야 한다. 컬럼 단위 설계와 다른 테이블과의 조인이 어렵다.
- 참고: A를 택해도 검색 함수를 LangChain `BaseRetriever`로 감싸면 LangChain·LangGraph와 연결할 수 있다.

### 4. `chunk`의 `kind='section'`(섹션 원문) 처리

- 상태: 논의 전 · 등록: 2026-11-11
- 현황: 섹션 전체 본문이 54개 들어 있다(최대 약 17만 자). 임베딩은 0개이고 `text`와 `raw`가 같다. 검색 청크로 쓰이지 않는다.
- 주의: 섹션 원문은 `text`/`table` 청크를 이어 붙여도 복원되지 않는다. 공시 상세 페이지의 원문 보기나 LLM 분석 컨텍스트로 쓰고 있을 수 있다.
- 선택지
  - A. 그대로 둔다
  - B. 별도 섹션(목차) 테이블로 옮긴다. `section_id`, 상위 섹션, 경로, 순서, 본문
  - C. 제거한다. 원본 XML을 따로 보관하고 필요할 때 렌더링한다.

### 5. `chunk`의 `kind='table'` 처리

- 상태: 논의 전 · 등록: 2026-11-11
- 현황: 표 하나가 `filing_table.cells`, 행 단위 `table` 청크, `table_kv` 청크로 세 번 저장된다. `table` 청크 1,705개 중 임베딩된 것은 278개다. 임시 데이터라 덜 된 것일 수 있다.
- 문제: 숫자 위주인 표를 임베딩하면 숫자의 의미가 담기지 않는다. 당기/전기, 연결/별도처럼 라벨이 같은 표가 많아서 검색 결과가 비슷한 표로 채워질 수 있다.
- 제안
  - 텍스트 청크에 관련 표의 `table_id`를 연결한다. 같은 섹션에서 텍스트 바로 뒤에 오는 표가 기준이다. 형태는 `chunk.related_table_ids text[]` 또는 연결 테이블 `chunk_table`이다.
  - 설명 텍스트가 거의 없는 재무제표 주석 표는 숫자를 뺀 표 설명 청크를 표 1개당 1개 만든다. 내용은 제목, 섹션 경로, 행·열 라벨, 단위, 기간, 연결/별도다.
  - 숫자는 청크에 두지 않고 항상 `filing_table`에서 읽는다.
- 참고: 재무제표 주석은 표 164개에 텍스트 청크가 16개뿐이라, 텍스트 연결만으로는 표를 찾기 어렵다.

### 6. `chunk`의 `text`와 `raw` 분리 여부

- 상태: 논의 전 · 등록: 2026-11-11
- 현황: `text`는 `[기업 | 공시 | 섹션]` 접두어와 `raw`를 합친 값이다. 모든 행에서 그렇다. `text`는 임베딩·검색용, `raw`는 화면 표시·근거 인용용이다.
- 선택지
  - A. 지금처럼 둘 다 저장한다.
  - B. `raw`만 저장하고, 임베딩할 때 `filing`과 `section_path`로 접두어를 만들어 붙인다.
- 참고: 절약되는 용량은 공시 1건에 약 3MB로 크지 않다. 공시 1건의 `chunk` 20MB는 대부분 임베딩이 차지한다.
